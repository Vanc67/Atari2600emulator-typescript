# a5xnu — модель Apple A5 (S5L8940x / k93ap) на Unicorn

Экспериментальная машинная модель SoC **Apple A5** (iPad 2 / iPhone 4s, кодовое имя
платы `k93ap`) и протокола загрузки ядра **XNU** поколения iOS 6 (`xnu-2107`, ARM32).

Написано с нуля на Python поверх **Unicorn** (движок QEMU TCG как библиотека).
QEMU в этой среде собрать нельзя — нет glib/pixman/SDL2/pkg-config/meson, а ставить
пакеты некуда, — поэтому CPU-эмулятор взят готовый (Unicorn ставится одним wheel'ом
с PyPI), а **вся модель платы, протокол загрузки, консоль, загрузчик Mach-O и
средства диагностики написаны здесь сами**.

**Никакая прошивка Apple не используется, не скачивается и не хранится.** В репозитории
нет ни одного байта чужой собственности: поток инструкций собирается прямо здесь из
опубликованного протокола загрузки.

## Как запустить

```bash
python3 -m venv /path/to/emuenv
/path/to/emuenv/bin/pip install unicorn capstone keystone-engine pycryptodome

cd a5xnu
/path/to/emuenv/bin/python demo_boot.py                    # наглядный прогон
/path/to/emuenv/bin/python -m unittest discover -s tests -v # все проверки
```

Проверено на unicorn 2.1.4, capstone 5.0.7, keystone-engine 0.9.2 (Python 3.11, Linux x86_64).

## Карта платы k93ap (A5)

| Область | Адрес | Размер | Что это |
|---|---|---|---|
| RAM | `0x40000000` | 2 ГБ | физическая память; `VA = PA + 0x40000000` |
| AIC | `0x0F200000` | `0x10000` | контроллер прерываний (`aic,1`) |
| UART0 | `0x02500000` | `0x100` | `uart-1,samsung` (раскладка exynos), irq 21 — **есть модель регистров** |
| UART3 / UART5 | `0x02800000` / `0x02A00000` | `0x100` | то же семейство — **есть модель** |
| PMGR | `0x0F100000` (+`0x08C/8D/8E/8F/A5/A600000`) | `0x7000` | менеджер питания |
| WDT | `0x0F103020` | `0x10` | сторожевой таймер, irq 4 |
| GPIO | `0x0FA00000` | `0x1000` | |
| NAND (FMI) | `0x01200000` | `0x190000` | `fmi,s5l8940x`, irq 33/34 |
| I2C0/1/2 | `0x032/33/3400000` | `0x1000` | PMU `d1946` на i2c0 @ `0x3C` |
| SGX | `0x05100000` | `0x10000` | GPU PowerVR |
| CLCD / MIPI | `0x0A100000` / `0x09500000` | `0x10000` | дисплей |
| SHA2 / PKE | `0x02000000` / `0x03100000` | `0x1000` | криптоускорители |
| arm-io | `0x3FB00000` | `0x200000` | |

Ключевые адреса загрузки: DeviceTree VA `0x8F000000` (PA `0x4F000000`, длина
`0x11FD8`), `boot_args` PA `0x4FF01000`, `topOfKernelData` `0x40DA0000`,
вход ядра VA `0x800860C8` / PA `0x400860C8`.

Всё, что смаплено, но не имеет модели регистров, **логируется**: каждый доступ
попадает в упорядоченный журнал. Именно так и восстанавливают семантику
периферии — следующим шагом это AIC.

## boot_args (xnu-2107, ARM32, 0x140 байт)

| Смещение | Поле | Значение |
|---|---|---|
| `+0x00` | Revision | 2 |
| `+0x02` | **Epoch** | **`0x12`** — `pe_identify_machine` сверяет его; при несовпадении печатается «Epoch Mismatch» и ядро зависает ещё до создания локов |
| `+0x04` | virtBase | `0x80000000` |
| `+0x08` | physBase | `0x40000000` |
| `+0x0C` | memSize | `0x20000000` |
| `+0x10` | topOfKernelData | PA |
| `+0x14` | Video | 24 байта, нули допустимы |
| `+0x2C` | machineType | 0 |
| `+0x30` | deviceTreeP | **VA** (не PA!) |
| `+0x34` | deviceTreeLength | |
| `+0x38` | CommandLine | 256 байт |
| `+0x138` | bootFlags | |
| `+0x13C` | memSizeActual | |

В `r0` ядру передаётся **физический** адрес `boot_args`; `start()` сам переводит его
в виртуальный (`0x4FF01000 → 0x8FF01000`).

## Что удалось выяснить по ходу (и что оказалось неверным в источниках)

Эти пункты стоили часов отладки, поэтому зафиксированы и покрыты тестами —
иначе их легко потерять.

### 1. `TTB = topOfKernelData | 0x4A` — так не бывает

Опубликованный worklog по k93ap утверждает именно это. Но:

* `0x40DA004A` **не выровнен на 16 КБ**, а таблица первого уровня ARMv7 обязана быть
  выровнена; `TTBR0[13:0]` аппаратурой игнорируется, так что младшие биты могут
  только разъехаться с программным циклом очистки;
* `0x4A` не является и дескриптором секции: бит 6 — SBZ, TEX живёт в битах `[14:12]`,
  а AP оказался бы нулевым, то есть **доступа нет вообще**.

Разбор по авторитетным определениям (`arch/arm/include/asm/pgtable-2level-hwdef.h`
из ядра Linux): `TYPE_SECT = 1<<0`, `BUFFERABLE = 1<<2`, `CACHEABLE = 1<<3`,
`XN = 1<<4`, `AP_WRITE = 1<<10`, `AP_READ = 1<<11`, `TEX(x) = x<<12`, `APX = 1<<15`.
Отсюда корректные флаги — **`0x40E`** = секция 1 МБ, write-back cacheable,
доступ только для привилегированного режима. `topOfKernelData` уже выровнен,
поэтому `TTB = topOfKernelData`.

### 2. Псевдонимы регистров ARM ломают транскрипцию

`r9 == sb`, `r10 == sl`, `r11 == fp`, `r12 == ip`. В листинге, где имена смешаны,
`mov sl, #0` незаметно обнуляет `memSize`, а флаг-регистр перезаписывает счётчик.
В `tests/test_a5_boot.py` распределение регистров выписано явно и задокументировано.

### 3. `bic rN, rM, #0x000FFFFF` не существует

20 единиц подряд не кодируются как «8 бит с поворотом». Обнуление битов `[19:0]`
делается парой `lsr #20` / `lsl #20`.

### 4. Маска декодирования cp15 была невыполнимой

Проверка `(insn & 0x0F000F10) == 0x0E000B10` требовала coproc == `0xB`, а следующая
строка — coproc == 15. Условие не выполнялось **никогда**, поэтому настоящие `mcr`
исполнялись, запись в TTBR0 вызывала prefetch abort (intno 3) и Unicorn ретраил её
вечно: **7 539 030 исключений за 20 секунд** плюс неограниченно растущий список.
Правильная маска — `0x0F000010` против `0x0E000010`, coproc проверяется отдельно.

Кодировки сверены с keystone: `mrc p15,0,r1,c1,c0,0 → 0xEE111F10`,
`mcr p15,0,r6,c2,c0,0 → 0xEE026F10`, `mcr p7,... → 0xEE011710` (отвергается).

### 5. Keystone считает `;` разделителем, а не комментарием

Листинг с комментариями `;` разбирался как `<инструкция> <случайные слова>`, что
давало либо `KS_ERR_ASM_MNEMONICFAIL`, либо **клин двухпроходного резолвера меток**.
Снаружи это выглядело как «тесты висят 478 секунд», хотя эмуляция занимала 0.1 с.
Комментарии теперь вычищаются до передачи в keystone.

### 6. `UC_HOOK_MEM_READ` не может вернуть значение

Возврат колбэка игнорируется, и CPU загружает то, что лежит в странице. Но хук
срабатывает **до** загрузки, поэтому значение публикуется в страницу через
`mem_write`. Проверено: хук без записи → устаревшее значение, хук с записью →
значение устройства. Без этого `UTRSTAT` читается нулём и любой цикл вывода
в консоль крутится вечно, ожидая передатчик.

### 7. Отказы приходят двумя разными путями

* через INTR-хук — prefetch/data abort на инструкции, которую Unicorn декодирует,
  но не может завершить (реальный `mcr` в TTBR0);
* как `UcError` из `emu_start` — инструкцию вообще не удаётся декодировать
  (`UDF` → `UC_ERR_INSN_INVALID`).

`run()` переживает оба: свидетельство сохраняется в `unimplemented` / `stalled` /
`fault`, вызов возвращается. Исключение наружу уничтожило бы состояние регистров —
единственное, что на этом этапе действительно ценно.

### 8. Прочее, измеренное, а не угаданное

* `uc.mem_map` отклоняет размер, не кратный странице (`mem_map(0x02500000, 0x100)` →
  `UC_ERR_ARG`), хотя device tree описывает UART0 именно как 0x100 байт. Окна
  округляются до страниц, смещения регистров остаются от неисходного основания.
* `uc.mem_regions()` возвращает **генератор**, а не список.
* Параметр `until` у `emu_start` почти ничего не стоит: 100k инструкций за ~0.35 с
  и с ним, и без него. Медленным оказался не он.
* Хук на каждую инструкцию с `mem_read`+`unpack` стоит ~1 млн инстр./с, с кэшем слов —
  ~4 млн инстр./с. Для 45 тысяч инструкций это несущественно.
* `mach_header_32` — ровно **28** байт, `segment_command` — ровно **56** байт.

## Что дальше

По порядку, каждый шаг проверяем сам по себе:

1. **AIC (`0x0F200000`)** — восстановить семантику регистров из журнала доступов.
   Linux `irq-apple-aic.c` описывает только AIC2, для A5 придётся выводить самим.
2. **Таймер** — в device tree отдельного узла таймера нет, значит он внутри PMGR
   или AIC; инициализацию нужно доставать из iBoot.
3. **Консоль** — должна появиться строка `Darwin Kernel Version 13.0.0…`.
4. **Цикл «паника → исправление»**, затем `rd=md0` (ramdisk/rootfs) и
   однопользовательская оболочка.

Отдельно нужны инструменты подготовки прошивки (спецификации есть, реализация
покрывается синтетическими тестами без чужих данных): распаковщик `complzss`
(вариант Okumura, кольцо 4096 байт, инициализированное пробелами, `dictptr = 4078`),
разбор и расшифровка IMG3 (магическое число — little-endian `"3gmI"`),
расшифровка DMG `encrcdsa` (FileVault V2: AES-128-CBC на блок 512 байт,
IV = `HMAC-SHA1(hmacKey, chunkNo)[:16]`, ключ — 72 hex-символа),
разбор ADT DeviceTree и правка узла `memory`.

## Правовая часть

Прошивка iOS — собственность Apple; её лицензия запрещает запуск на не-Apple
оборудовании, а обход защиты подпадает под DMCA §1201. Все существующие проекты
остаются в правовом поле именно тем, что **не распространяют файлы Apple**:
пользователь сам получает IPSW с серверов Apple, а ключи берутся с theiphonewiki.
Здесь не хранится и не скачивается ни одного байта прошивки — только код.

Приложения для Android под названием «эмулятор iOS» — мошенничество и/или вредоносное
ПО; рабочей реализации A5 для Android в этой среде тоже нет.

## Отношение к существующим работам

Единственная известная модель A5 — `hw/arm/k93ap.c` в `b1ackmarket/qemu-n90ap`
(fork QEMU). Она доведена до фазы конструкторов kext, но без консоли, без графики
и без оболочки. Открытых загрузок iOS 6 с графикой не существует — это и есть
граница исследования.

Модели QEMU покрывают S5L8900, S5L8720, S5L8920, S5L8922, **A4/S5L8930 (потолок)**,
далее прыжок сразу к A9 (только UART), A13 (полная графика) и плате `virt` с ядром
собственной сборки. **Для A5, A6 и A7 — ровно поколения iOS 8/9 — готовых моделей
нет.** Промежуточные выводы по всем этим проектам собраны в `../ios-on-qemu/`.
